# Triage

Move **incoming work from other people** through the project's configured triage state machine. Do not triage tickets produced by `to-tickets`; those are already agent-ready by construction.

This is a user-invoked workflow. Skill names are canonical names, not host command syntax.

## Preconditions and sources of truth

The repo's configured issue tracker and triage-label mapping must already be available. If either is missing, stop before mutation and tell the user to invoke the user-invoked `setup-matt-pocock-skills` workflow explicitly using their harness's invocation mechanism.

Use these sources authoritatively:

- **Tracker operations and storage shape:** the repo's configured issue-tracker document.
- **Canonical state role → actual label/status string:** the configured triage-label mapping.
- **Agent-ready brief shape:** [AGENT-BRIEF.md](AGENT-BRIEF.md).
- **Rejected-enhancement memory:** [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md).

Do not duplicate tracker commands here, guess label strings, or create a canonical label merely because the configured tracker uses another name.

## State machine

Classify each item as one category for triage reasoning and briefs:

- `bug` — existing behavior is broken.
- `enhancement` — new or improved behavior is requested.

Persist the category only if the configured tracker already defines how categories are represented.

Five canonical state roles:

- `needs-triage` — maintainer evaluation is in progress.
- `needs-info` — reporter input is required.
- `ready-for-agent` — the work is specified well enough for an agent.
- `ready-for-human` — the next implementation step requires a human.
- `wontfix` — the request will not be actioned.

A triaged item has exactly one state role. If existing state roles conflict, stop and ask the maintainer which state is authoritative before any other mutation.

Normal transitions are:

```text
untriaged -> needs-triage
needs-triage -> needs-info | ready-for-agent | ready-for-human | wontfix
needs-info -> needs-triage   (after reporter activity since the last triage note)
```

If the requested transition is not listed above, point that out before mutation. Follow the maintainer's explicit direction if they confirm it.

If the configured tracker includes external PRs/MRs as a request surface, apply the same machine to them. A `ready-for-agent` PR/MR has a brief describing what remains to be done to the existing diff; `ready-for-human` means the next implementation step is human-only.

## Mutation invariants

Before any triage-state mutation, persist work-item role `request`. Work-item role is independent from category and triage state.

Every AI-authored tracker note created during triage must start with:

```markdown
> *This was generated by AI during triage.*
```

After mutation, re-read the tracker item and verify work-item role `request` and exactly one intended triage state.

## Route the request

Interpret the maintainer's natural-language request:

- **Move one specific item to an explicitly named canonical state** — read [TRIAGE-ITEM.md](TRIAGE-ITEM.md) and follow its explicit state-override path.
- **Triage one specific item without an explicitly requested target state** — read [TRIAGE-ITEM.md](TRIAGE-ITEM.md) and follow the standard triage path.
- **Show incoming work needing attention, or work already ready for agents** — read [QUEUE.md](QUEUE.md).

Do not translate these requests into host-specific command syntax.

## Phase boundary

Triage prepares work; it does not implement it. If the user asks to continue from a `ready-for-agent` item into implementation, tell them that `implement` is the user-invoked next workflow and that they must invoke it explicitly. Do not invoke, read, shell out to, or emulate `implement`.
