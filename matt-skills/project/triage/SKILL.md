# Triage

Move incoming work on the project's configured issue tracker through a small state machine of triage roles.

This is a **user-invoked** workflow. Skill names below are canonical names, not host command syntax. When another user-invoked workflow is the next phase, tell the human which skill to invoke explicitly using their harness's user-invocation mechanism; do not invoke, read, shell out to, or emulate that workflow yourself.

The issue tracker and triage label vocabulary should already have been configured by `setup-matt-pocock-skills`. If they have not been provided, stop before mutating anything and tell the user to invoke that user-invoked skill explicitly. Do not guess tracker commands or label strings.

If this repo treats external pull requests or merge requests as a request surface (see the issue-tracker config), triage covers them too: **a PR/MR is an issue with attached code**, using the same roles, states, and machine, with a few deltas marked below. Resolve ambiguous references according to the configured tracker.

Every triage note, agent brief, or other comment published to the issue tracker **must** start with this disclaimer:

```markdown
> *This was generated by AI during triage.*
```

For a local-markdown tracker, the same disclaimer starts each AI-authored entry appended under `## Comments`.

## Reference docs

- [AGENT-BRIEF.md](AGENT-BRIEF.md): how to write durable agent briefs

## Roles

Two **category** roles:

- `bug`: something is broken
- `enhancement`: a new feature or improvement

Five canonical **state** roles:

- `needs-triage`: maintainer needs to evaluate
- `needs-info`: waiting on the reporter for more information
- `ready-for-agent`: fully specified, ready for an agent
- `ready-for-human`: needs human implementation
- `wontfix`: will not be actioned

The state-role names are canonical. The actual label strings used by the configured tracker may differ; always use the mapping supplied by `setup-matt-pocock-skills`. Never create a duplicate canonical label just because the configured string is different.

For a PR/MR, the same states are read against the attached code: `ready-for-agent` means a brief is attached and an agent should take the next step on the diff; `ready-for-human` means it is ready for a human-only next step such as merge, privileged access, or a judgment call.

Every triaged item should carry exactly one category role and one state role. If state roles conflict, flag the conflict and ask the maintainer before doing anything else.

For a **local-markdown tracker**, represent the roles near the top of the issue file as:

```markdown
Category: bug | enhancement
Status: <configured state-role string>
```

Conversation history and generated notes append under `## Comments`; do not overwrite the original report.

State transitions: an unlabeled/unclassified item normally enters `needs-triage`; from there it moves to `needs-info`, `ready-for-agent`, `ready-for-human`, or `wontfix`. `needs-info` returns to `needs-triage` once the reporter replies. The maintainer can override at any time; flag transitions that look unusual and ask before proceeding.

## Invocation

The maintainer invokes the user-invoked `triage` skill and describes what they want in natural language. Interpret the request and act. Examples:

- "Show me anything that needs my attention"
- "Let's look at #42"
- "Move #42 to ready-for-agent"
- "What's ready for agents to pick up?"

Do not rewrite these into slash commands or another host-specific trigger syntax.

## Show what needs attention

Query the configured issue tracker and present three buckets, oldest first:

1. **📭 Unlabeled / unclassified** — never triaged.
2. **🔄 `needs-triage`** — evaluation in progress.
3. **💬 `needs-info` with reporter activity since the last triage notes** — needs re-evaluation.

For local markdown, "unlabeled" means an incoming issue file without a `Status:` line, and reporter activity means new human-authored content under `## Comments` after the last AI triage note.

When PRs/MRs are in scope, include external ones in these buckets and tag each line `[PR]`, `[MR]`, or `[issue]`. Discovery surfaces only *external* code submissions according to the tracker config; a collaborator's in-flight branch is not triage work. This filter is discovery-only: an explicitly named PR/MR is always triaged regardless of author.

Show counts and a one-line summary per item. Let the maintainer choose by list position, tracker id, URL, or local path.

## Triage a specific issue or PR/MR

1. **Gather context.** Read the full item: body, comments/notes, labels, author, and dates; for a PR/MR, read the diff too. For local markdown, read the whole issue file including `## Comments`. Parse prior triage notes so resolved questions are not asked again.

   Explore the codebase using the project's domain glossary and respect ADRs in the area being touched; every ADR present should be treated as a current architectural decision unless the repo explicitly says otherwise.

   Run two checks against the codebase:

   - **Redundancy:** search for an existing implementation of the requested behavior by domain concept, not only by the reporter's wording, and report where you looked. If the behavior already exists, the outcome is an already-implemented `wontfix` in step 5.
   - **Prior rejection:** read `.out-of-scope/*.md` and surface any entry that resembles this request.

2. **Recommend.** Tell the maintainer your category and state recommendation with reasoning, plus a brief codebase summary relevant to the request, including whether it appears already implemented. Wait for direction before changing tracker state.

3. **Verify the claim.** Before any grilling, check whether the claim holds up.

   - For a bug, reproduce it from the reporter's steps when the environment permits.
   - For a PR/MR, verify that the diff does what it claims by inspecting/checking out the contribution as appropriate and running the relevant tests or commands.
   - For a local report, use the same verification standard; tracker shape does not lower the evidence bar.

   Report one of: confirmed (with the relevant code path or behavior), failed to reproduce/verify, or insufficient detail. Insufficient detail is a strong `needs-info` signal. A confirmed verification makes the eventual agent brief stronger.

4. **Grill if needed.** If the request needs product or design clarification, call the Skill tool twice, for `grilling` and `domain-modeling`, and grill it into shape a round of questions at a time. Sharpen domain terms and update `CONTEXT.md`/ADRs inline as durable decisions land.

   These are model-invoked supporting skills. If either is unavailable in the current harness and the clarification cannot be completed safely without it, say that the dependency is unavailable rather than emulating the missing skill by reading its `SKILL.md` directly.

5. **Apply the outcome** using the configured tracker operations and the configured state-label mapping:

   - `✅ ready-for-agent` — publish an agent brief ([AGENT-BRIEF.md](AGENT-BRIEF.md)), then apply exactly one category and the configured `ready-for-agent` state.
   - `🧑 ready-for-human` — use the same durable structure as an agent brief, but state why the work cannot be delegated: judgment calls, privileged/external access, unresolved design authority, or manual testing.
   - `💬 needs-info` — publish triage notes using the template below and apply the configured `needs-info` state.
   - `🚫 wontfix` — apply the configured terminal state and close the tracker item where the tracker has a close operation:
     - **Already implemented** — point to the existing behavior. Do **not** write to `.out-of-scope/`; that knowledge base is for rejected requests, not built features.
     - **Rejected bug** — explain the decision politely, then close/terminally mark it.
     - **Rejected enhancement** — write or update the matching `.out-of-scope/` record, reference it from the closing note, then close/terminally mark it ([OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)).
   - `🔄 needs-triage` — apply the configured role. A progress note is optional.

   For local markdown, changing `Status:` to `wontfix` is the terminal equivalent of closing the item; retain the file and its history.

6. **Stop at the triage boundary.** Triage classifies, verifies, and prepares work; it does not implement it. If the maintainer wants a `ready-for-agent` item built now, tell them that the user-invoked `implement` skill is the normal next workflow and that they must invoke it explicitly using their harness's user-invocation mechanism. Do not invoke or emulate `implement` yourself.

## Quick state override

If the maintainer says "move #42 to ready-for-agent", trust the override. Confirm the concrete mutation you are about to make: category if needed, removal of conflicting state roles, the configured target state string, any comment/brief, and whether the item will close. Then execute.

Skip grilling. If moving to `ready-for-agent` without a prior grilling session or durable brief, ask whether the maintainer wants an agent brief written before applying the final state.

## Needs-info template

```markdown
> *This was generated by AI during triage.*

## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

Capture everything resolved during grilling under "established so far" so the work is not lost. Questions must be specific and actionable, not "please provide more info".

## Resuming a previous session

If prior triage notes exist, read them, check whether the reporter answered any outstanding questions, and present the updated picture before continuing. Do not re-ask resolved questions.
