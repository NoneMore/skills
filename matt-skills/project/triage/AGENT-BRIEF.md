# Writing Agent Briefs

An agent brief is a durable structured note attached to a configured tracker item when it moves to the canonical `ready-for-agent` state. On GitHub/GitLab it is normally a comment/note on an issue, PR, or MR. On a local-markdown tracker it is appended under the issue file's `## Comments` section.

The original report and discussion are context; the agent brief is the execution contract.

Every published brief must begin with the triage disclaimer:

```markdown
> *This was generated by AI during triage.*
```

The brief states **what the agent should do**. For an issue, that usually means building the requested change from the current codebase. For a PR/MR, it means what remains to be done *to the existing diff*: finish it, close gaps, address review points, or verify it. The same principles apply to both.

## Principles

### Durability over precision

An item may sit in `ready-for-agent` for days or weeks while the codebase moves underneath it. Write the brief so it remains useful across renames, moves, and refactors.

- **Do** describe interfaces, types, behavioral contracts, invariants, and externally observable outcomes.
- **Do** name stable symbols or conceptual interfaces when that helps an agent find the right seam.
- **Don't** rely on file paths as the contract.
- **Don't** cite line numbers.
- **Don't** assume the current implementation structure will remain unchanged.

A file path may be mentioned only as supporting context when no more durable identifier exists; it must never be the acceptance contract.

### Behavioral, not procedural

Describe **what** the system should do, not a step-by-step implementation recipe. The implementing agent will explore the current codebase and make local implementation decisions.

- **Good:** "The `SkillConfig` contract accepts an optional `schedule` field of type `CronExpression`."
- **Bad:** "Open a particular source file and add a field on line 42."
- **Good:** "Invoking the triage workflow without a target shows a summary of incoming items that need attention."
- **Bad:** "Add a switch statement to the main handler."

### Complete acceptance criteria

Every brief needs concrete, independently verifiable completion criteria.

- **Good:** "Items in the configured `needs-triage` state are returned by the tracker's attention query."
- **Bad:** "Triage should work correctly."

Prefer criteria at the highest useful behavioral seam already present in the codebase.

### Explicit scope boundaries

State what is out of scope so the implementing agent does not gold-plate or silently absorb adjacent requests.

### Preserve tracker abstraction

Use the configured tracker's identity format in references:

- GitHub/GitLab: issue/PR/MR ids or links.
- Local markdown: repo-relative issue paths.

Do not hard-code GitHub-specific commands or label strings into the brief unless the requested behavior itself is GitHub-specific.

## Template

```markdown
> *This was generated by AI during triage.*

## Agent Brief

**Category:** bug / enhancement
**Summary:** one-line description of what needs to happen

**Current behavior:**
Describe what happens now. For bugs, this is the broken behavior.
For enhancements, this is the status quo the feature builds on.
For PRs/MRs, describe what the current diff already does and what is still missing.

**Desired behavior:**
Describe what should happen after the agent's work is complete.
Be specific about edge cases and error conditions.

**Key interfaces:**
- `TypeName`: what needs to change and why
- `functionName()` contract: current vs desired behavior
- Config shape or protocol: any new externally meaningful option or invariant

**Acceptance criteria:**
- [ ] Specific, testable criterion 1
- [ ] Specific, testable criterion 2
- [ ] Specific, testable criterion 3

**Out of scope:**
- Thing that should NOT be changed or addressed
- Adjacent feature that may look related but is separate
```

## Examples

### Good agent brief: bug

```markdown
> *This was generated by AI during triage.*

## Agent Brief

**Category:** bug
**Summary:** Skill description truncation must not cut words in half

**Current behavior:**
When a skill description exceeds the maximum length, truncation can stop in the
middle of a word and produce broken human-facing text.

**Desired behavior:**
Truncation should stop at the last word boundary that fits and append an
ellipsis without exceeding the configured maximum length.

**Key interfaces:**
- The skill metadata description contract: no schema change is required
- The parser/normalizer that produces the final description string

**Acceptance criteria:**
- [ ] Descriptions under the limit are unchanged
- [ ] Over-limit descriptions end at a word boundary
- [ ] Truncated descriptions end with an ellipsis
- [ ] The final value remains within the configured maximum length

**Out of scope:**
- Changing the maximum-length policy
- Adding a new multi-line description format
```

### Good agent brief: enhancement

```markdown
> *This was generated by AI during triage.*

## Agent Brief

**Category:** enhancement
**Summary:** Persist rejected feature concepts in an out-of-scope knowledge base

**Current behavior:**
A rejected feature request can be closed with an explanation, but the durable
reasoning is difficult to discover when a similar request arrives later.

**Desired behavior:**
Rejected enhancement concepts should be recorded under `.out-of-scope/` with
the decision, durable reasoning, and references to prior requests. New triage
sessions should surface a conceptually matching prior rejection.

**Key interfaces:**
- The markdown record format for one rejected concept
- The triage workflow's prior-rejection lookup

**Acceptance criteria:**
- [ ] Rejecting an enhancement creates or updates one concept record
- [ ] The record contains durable reasoning and a request reference
- [ ] A matching concept reuses the existing record instead of duplicating it
- [ ] Triage surfaces relevant prior rejection records before recommending state

**Out of scope:**
- Fully automated semantic matching without maintainer confirmation
- Reopening historical requests automatically
- Treating already-implemented features as rejected concepts
```

### Good agent brief: PR/MR

For a code contribution, "Current behavior" describes the state of the diff and the brief asks the agent to finish or repair it rather than rebuild from zero.

```markdown
> *This was generated by AI during triage.*

## Agent Brief

**Category:** enhancement
**Summary:** Finish structured output support in the contributor's triage change

**Current behavior:**
The contribution adds structured output for the successful path, but error
paths still emit human text and the new mode lacks coverage.

**Desired behavior:**
When structured output is requested, both success and error paths produce the
same documented machine-readable format while exit semantics remain unchanged.
The default human-readable output must remain unaffected.

**Key interfaces:**
- The command's structured-output error contract
- The serializer already introduced by the contribution

**Acceptance criteria:**
- [ ] Structured output is valid for success and failure cases
- [ ] Exit behavior matches the existing command contract
- [ ] Tests cover one success and one failure case
- [ ] Default human-readable output is unchanged

**Out of scope:**
- Adding structured output to unrelated commands
- Redesigning the contribution's already-approved success payload
```

## Bad agent brief

```markdown
## Agent Brief

**Summary:** Fix the triage bug

**What to do:**
The triage thing is broken. Open the main file and fix the function around
line 150.

**Files to change:**
- some/source/file.ts
- another/source/file.ts
```

This is bad because it has no category, no stable behavioral contract, no acceptance criteria, no scope boundary, and depends on brittle implementation locations.
