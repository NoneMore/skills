# Setup Tracker

Configure tracker storage only. Read [ISSUE-MODEL.md](ISSUE-MODEL.md), then only the selected backend document. Publish both as a self-contained contract at `docs/agents/issues.md`.

## 1. Choose backend

Use an explicit backend choice. Otherwise use the one unambiguous intended GitHub repository; ask if several are plausible; use Local Markdown when no GitHub repository is intended.

## 2. Inspect

Read `docs/agents/issues.md` if present. Backend identity is the backend plus its target: GitHub repository identity or Local Markdown issue root.

- Same identity: make only missing setup changes and rebuild the contract.
- Different identity: stop unless the user explicitly requested replacement. Replacement changes setup artifacts only; it does not migrate existing issues.

For GitHub, confirm repository identity, Issues availability, label read/write access, and existing tracker labels. For Local Markdown, inspect `.tracker/issues/`.

Setup may change only configuration artifacts and required backend resources. Never classify, repair, close, relabel, or otherwise modify existing issues, and do not modify issue templates.

## 3. Configure

For GitHub, ensure all required tracker labels exist while preserving unrelated labels. For Local Markdown, ensure `.tracker/issues/` exists without rewriting issue files. Native relation capabilities are checked only by workflows that use them.

## 4. Publish and verify

Replace `docs/agents/issues.md` with this header followed by the complete current `ISSUE-MODEL.md` and selected backend document:

```markdown
<!-- Generated by setup-tracker. Do not edit directly; re-run setup-tracker to rebuild. -->
# Issue tracker
Backend: <github|local-markdown>
Repository: <owner/repo>        # GitHub only
Issue root: .tracker/issues/    # Local Markdown only
```

The result must be self-contained and deterministic: no Skill-relative dependency, no appended stale content, and an unchanged same-identity rerun produces the same file.

Only when explicitly requested, wire the tracker into project instructions by adding or updating one pointer to `docs/agents/issues.md` that says it contains the tracker contract and should be read before classifying, creating, or updating tracked work. Use the environment's instruction-authoring mechanism or effective runtime instruction target; do not guess a filename.

Verify the required backend resources and that the generated contract names the intended identity and exactly contains the current model plus selected backend representation. Report the configured backend and stop.
